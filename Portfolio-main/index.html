AI Job Seeker Platform

Problem: Job hunting means manually tailoring a resume per posting, judging fit yourself, and tracking every application's status by hand — a repetitive process that's a good fit for automation.

Overview: A full-stack platform that automates the resume-to-application pipeline — parses an uploaded resume with an LLM into structured data, embeds it for semantic job matching, generates ATS-optimized resume rewrites, and can auto-apply through site-specific adapters — coordinated end-to-end by an event-driven Celery pipeline.

Architecture & workflow
Resume upload→ LLM parse→ pgvector embed→ ATS score→ semantic match→ dashboard (WebSocket)→ notify
Main features
  • ▸LLM-based resume parsing into structured data
  • ▸Semantic job matching via pgvector embeddings
  • ▸ATS resume scoring + LLM-assisted rewrite (DOCX/PDF)
  • ▸Auto-apply via Greenhouse/Lever APIs + Playwright
  • ▸Real-time dashboard updates over WebSocket
  • ▸Gmail-based application-status tracking (LLM classification)
FastAPI SQLAlchemy (async) PostgreSQL + pgvector Redis Celery React 19 + TypeScript Vite Docker + nginx Ollama / Claude / OpenAI / Gemini / Groq Playwright
GitHub Repository
Data processing

Resumes are uploaded as PDF/DOCX, text-extracted with pypdf/python-docx, then passed to an LLM for structured extraction into typed fields (skills, experience, education).

Model / LLM selection

A pluggable AI-provider layer: Ollama (local) by default for dev, swappable to Claude, OpenAI, Gemini, or Groq via one environment variable — used for resume parsing, email classification, job-skill extraction, and ATS resume rewriting.

Embeddings & retrieval

Resumes and job postings are embedded (local sentence-transformers, 384-dim, by default — swappable to Voyage/OpenAI/Gemini) and stored in Postgres via pgvector. Matching combines cosine similarity with explicit skill-overlap scoring and rule-based boosts, not embeddings alone.

Backend architecture

A modular monolith — 14 feature modules in one FastAPI process, each following router → service → repository → model layering. Cross-module coordination runs through direct Celery task chaining and Redis pub/sub, not the custom event bus I built (which, per my own architecture audit, ended up wired but unused — real coordination happens elsewhere).

Database design

PostgreSQL with 40 tables across the 14 modules, SQLAlchemy ORM + Alembic migrations, and the pgvector extension for similarity search alongside the relational data.

API integration

A versioned REST API (/api/v1/*) documented via Swagger/ReDoc; Gmail API (OAuth) for application-status email polling; Greenhouse/Lever HTTP APIs plus Playwright browser automation for the ATSs that don't expose one.

Deployment architecture

Fully containerized with Docker Compose — nginx as the single public entry point, proxying to the API and the frontend. Built and verified locally; not deployed to a public environment yet.

Challenges & limitations

I ran a full self-audit of the codebase rather than assume it worked end-to-end, and documented the real gaps: the in-process event bus was built but never actually wired to anything; push notifications are a no-op placeholder; and the AI Career Coach tools don't auto-trigger after a resume finishes processing — they're manual, on-demand only.

FinOps Devta — GCP Cost Estimation Platform

Problem: Estimating and optimizing Google Cloud spend is usually manual and disconnected from real pricing data — teams need a fast way to turn business requirements into a validated, priced architecture with a clear audit trail.

Overview: A full-stack FinOps platform that turns customer requirements — entered via a wizard, an uploaded Excel sheet, or free text — into a validated architecture recommendation, priced against the real Google Cloud Billing Catalog API, with exportable Excel/PDF proposals, rightsizing and committed-use-discount recommendations, and GCP/AWS/Azure cost comparison.

Architecture & workflow
Requirement intake→ 13-rule validation→ normalization→ AI recommendation→ live GCP pricing→ Excel / PDF report→ audit log
Main features
  • ▸Live Google Cloud Billing Catalog API pricing, not hardcoded
  • ▸Excel + free-text natural-language requirement intake
  • ▸13-rule validation + strategy-based normalization, fully audited
  • ▸Rightsizing, committed-use-discount, forecast & carbon estimates
  • ▸GCP / AWS / Azure cross-cloud cost comparison
  • ▸Versioned project/estimate history, JWT auth + RBAC
FastAPI SQLAlchemy + Alembic PostgreSQL (Neon) Redis + Celery Next.js 16 + TypeScript Tailwind CSS Google Cloud Billing API Groq (LLM) Docker + Kubernetes GitHub Actions CI/CD
GitHub Repository Live Demo
Data processing

Three intake paths into one shared schema: an interactive wizard, an Excel questionnaire (the blank template and the parser are generated from the same field schema, so they can't drift apart), and free-text natural-language extraction.

Model / LLM selection

Groq powers optional plain-English explanations and an AI assistant chat; both degrade gracefully (deterministic template text, or a 503) when no Groq key is configured. The core estimation/pricing engine itself is fully deterministic and doesn't depend on an LLM — the free-text extractor is explicitly rule-based today, documented as a drop-in point for an LLM later.

Embeddings & retrieval

Not used here — GCP SKU matching is done via structured catalog lookups (machine family, disk type, GPU type, region) against the real Cloud Billing Catalog API, not vector search.

Backend architecture

Layered engines — validation → normalization → recommendation → architecture → pricing — each sitting behind an interface (CatalogProvider, PricingProvider) so mock data, live GCP pricing, and mock AWS/Azure providers are interchangeable with zero business-logic changes.

Database design

SQLAlchemy models for users, projects, estimate_versions, and audit_log_rows. Every save creates a new immutable, auto-incrementing estimate version instead of overwriting — full history stays reloadable and re-exportable.

API integration

The real Google Cloud Billing Catalog API (cloudbilling.googleapis.com) with SKU matching, pagination, retry, and a Redis-backed cache (in-memory fallback); the Groq API for the optional LLM features.

Deployment architecture

Vercel (Next.js frontend) + Render (FastAPI backend, Docker) + Neon (serverless Postgres) on the free tier — verified live. A separate Kubernetes manifest set exists for a real cluster but, per my own deployment docs, was validated structurally and never applied to a live cluster.

Challenges & limitations

Redis and the Celery worker are skipped on the free-tier deploy (Render's free plan has no background-worker service), so async report/batch jobs accept requests but stay queued rather than completing — a documented gap, not a hidden one. AWS/Azure pricing is mock-only so far (no live Pricing/Retail Prices API integration yet), and live GCP pricing was validated against realistic mocked API responses before a real end-to-end credential run.

Llama 3.1 Cold Email Generator

Problem: Writing a tailored cold email for every job posting is repetitive. Overview: A Streamlit app that scrapes a job posting URL, extracts structured job data with an LLM, retrieves the most relevant portfolio projects via vector similarity, and generates a tailored email referencing them.

Flow: URL scraped (WebBaseLoader) → text cleaned (regex) → LLM extracts job JSON (role/skills/description) → skills query ChromaDB for top-2 matching portfolio links → LLM writes the email referencing them.
LangChain Groq (Llama 3.1 70B) ChromaDB Streamlit Pandas
GitHub Repository

Model: Llama 3.1 70B (llama-3.1-70b-versatile) served via Groq's inference API, for both job-data extraction and email writing — chosen for inference speed over running the model locally.

Retrieval: ChromaDB's default embedding function indexes a small CSV of tech-stack → portfolio-link pairs; extracted job skills query it for the 2 most relevant links. This is lightweight retrieval, not a full RAG question-answering pipeline.

Limitations: depends on the target page being scrapeable (no JS-rendered career pages) and the LLM returning valid JSON — it fails with a clear error rather than silently breaking, but doesn't yet auto-retry a bad parse. Runs locally only; not deployed.

Object Detection — SSD MobileNet

Problem: Real-time object/person detection needs a model accurate enough to be useful and fast enough to run without data-center GPUs. Overview: A transfer-learning pipeline on the TensorFlow 2 Object Detection API, fine-tuning an SSD MobileNet backbone for real-time detection, trained on COCO-format annotations.

Flow: COCO-format dataset → TFRecord conversion (TF Object Detection API) → transfer learning on COCO-pretrained SSD MobileNet → TensorBoard-monitored training → exported inference graph.
TensorFlow 2 SSD MobileNet COCO API CUDA / cuDNN Python
GitHub Repository

Model selection: SSD MobileNet — a single-shot detector on a MobileNet backbone, chosen specifically for real-time inference speed over a heavier two-stage detector like Faster R-CNN.

Data processing: COCO-format annotations converted to TFRecords through the TF Object Detection API's standard input pipeline.

Limitations: environment setup for the TF2 Object Detection API (protobuf compilation, matched CUDA/cuDNN/TensorFlow versions) is notoriously fragile — the repo's README documents the exact pinned versions needed for a working install. Local training/inference only; no exported model served publicly.
